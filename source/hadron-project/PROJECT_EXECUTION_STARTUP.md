# Project execution startup - revision80

This is cooperating-host exclusion, not an OS sandbox. Live project editing and commands remain disabled.

Electron configures the canonical <owned Hadron profile>/project-execution ledger in hadronBootstrap before the main server graph initializes legacy runtimes. Standalone entry configures its owned data directory before starting the server. Utility children receive a pinned copy of the frozen parent profile and mode; their first bootstrap import configures the same ledger and admits the child before dispatch. Mutating process environment variables later cannot redirect the trusted fork adapters to a different profile. Unconfigured embedders cannot acquire project authority.

A standard session retains the normal legacy tool workflow. An actual legacy start makes project admission unavailable, durably. Finishing its promise, reloading a window or starting a new host does not clear that record: arbitrary descendants/timers may survive. A standard host cannot begin legacy work while any cooperating host holds a project record.

The launch flag --hadron-project-session selects a project-only session for the entire process. It is not a renderer setting or permission grant. It skips inherited hook/custom-tool seeding, custom/skill/MCP registry startup, utility process creation and LSP startup. The ordinary built-in handler registrations remain guarded and cannot execute. Persisted pending jobs are loaded for inspection/cancellation but remain pending on disk with their original arguments. They are not automatically queued. Lost running jobs keep an explicit failed/not-replayed result. The health response reports the session mode, gate readiness, actual utility availability and held pending count without scope IDs, paths or credentials. This boot flag is an integration primitive, not a new user-facing project entry yet.

A project session refuses legacy execution even before its first scope and after releasing a scope. It cannot downgrade itself, switch profile or clear history. No caller can use a later initialize call to resume the held queue in that process. Already persisted legacy/project records remain held. Do not tell users to remove execution.json or change database rows. Existing user chats and saved logs remain the live accepted workflow; previous-process recovery, native grants, role admission and remaining execution-path audits precede editing activation.

Validation uses real built Windows Electron/server cold starts in disposable profiles with utility mode requested. Project-only startup stays clean, holds a seeded pending job unchanged, does not import the supplied custom implementation and launches no utility. Standard startup actually initializes the utility runtime and records legacy activity. A separate built native-reader fixture confirms bounded read, revoke and blocked send still work, using a simulated folder picker/provider. Neither fixture accesses personal projects or real subscriptions.


If the ledger cannot be constructed or its record is corrupt, the boot is marked startupBlocked and the server still opens in restricted inspection mode. All inherited startup work and execution are denied, including when failure occurred before the gate obtained a ledger. Reinitializing the same host cannot clear this state. A late-observed legacy start is persisted before refusing project-only configuration, so a second host cannot interpret an empty marker directory as a clean epoch. An actual built corrupt-record cold start verifies viewer/server availability, no utility startup and unchanged damaged evidence. An unreadable/invalid profile itself still fails boot rather than silently selecting another user's storage.

## Revision86 - confine theme maintenance to pinned profile storage (2026-11-07)

ExecutionStartup now pins a PrivateProfilePaths policy to the actual profile's BigInt device/inode. Internal consumers can recheck existing ancestors and leaves; linked/junction paths, hard-linked files, invalid ancestors, alternate streams, escapes and replaced profile roots are refused. Reinitializing the same string path cannot adopt a replacement root. This is a host storage check, not a model/project permission or an OS sandbox.

Theme initialization and CRUD in configured desktop/standalone/utility hosts now use the fixed profile/.ygg/custom-themes directory. A late external directory override is rejected before mutation. Target checks run on initialization, copying, listing, reading, saving and deletion. Template links/hard links are refused; copy uses exclusive-create semantics and rechecks a raced target. Saves open without truncation, validate the actual file handle/name/links first, and then write. Normal private theme operations do not taint a held project session. Unconfigured legacy test hosts retain their existing root resolution, but cannot obtain project execution authority.
