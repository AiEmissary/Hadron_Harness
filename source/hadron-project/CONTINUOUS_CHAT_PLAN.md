## Persistent state and scheduling rules

Use a dedicated private hadron-continuous-chat.db for sessions, turns and events. Session state: prepared, running, pause_requested, paused, stop_requested, stopped, completed, failed or needs_recovery. A turn records ordinal, role, parent turn, frozen prompt/history digest, actual model, status, response, provider handle/run/stream identities and reported usage. A unique session+ordinal and a single admitted current turn prevent duplicate dispatch. Include owner/workspace in all authorization checks; an unguessable ID alone is not ownership.

Within one database transaction reserve the next ordinal and the request budget before dispatch. Persist the actual native binding in onPrepared before it can spend. The main run database and continuous database cannot pretend to share an atomic transaction: if a crash splits reservation/binding, mark the request ambiguous and inspect the actual run; never create a second one. A duplicate completion for the same actual binding is idempotent. A mismatched, late, foreign or out-of-order completion cannot advance the scheduler. Persist the response and terminal event before scheduling the successor on a later event-loop turn, so Stop can interpose.

Pause requested during a turn lets that turn finish, saves it and schedules no next turn. Stop cancels the actual current worker and schedules no successor. Neither reports fully stopped until the worker has actually ended. Stop requested in the dispatch gap closes admission before spawn. Errors or unavailable models pause/fail visibly with no automatic provider retry. Graceful Quit cancels/joins and checkpoints; force-kill or lost connection enters recovery, not automatic continuous execution on startup. Resume is an explicit user action after reconciliation, with a fresh bounded permission/budget check and no reinterpretation of an old serialized capability.

User messages enter an ordered pending queue while a turn runs, then are frozen into the next turn at the boundary. They do not rewrite an in-flight prompt or already saved response. Branching from an earlier turn creates a separate paused/prepared session with only the selected ancestry, never siblings. Changing models/goals/permissions requires a deliberate boundary action and a recorded event. Start/resume clicks use request IDs and expected session revisions so multiple windows cannot launch the same turn twice.

## Budgets and memory

Start with an explicit maximum request count and maximum elapsed session duration; suggest20 turns and10 minutes for first testing, with visible settings for longer conversations. The active turn also has its own provider timeout. Pause visibly at the chosen limit; the user can extend and resume without manually sending each turn. Count every admitted request, including failures and optional future compaction; report token usage only when the provider supplies it. Subscription rate limits and costs cannot be inferred from invented token/dollar estimates.

Keep the authoritative transcript on disk. Build context from the selected ancestry plus the current user goal, model role and queued messages, within a declared character/turn budget. Do not repeatedly scan whole source files or include unrelated branches/logs. When context is too large, pause with an explicit choice to compact or fork; a summary remains marked as a summary and links back to its source turn range. Never silently discard disagreements or claim that a compressed memory is the original evidence. Optional summary generation is separately budgeted and saved with its actual run identity.

Repeated identical outputs, protocol failures, timeouts, exhausted budgets or stalled progress pause visibly. End-of-task suggestions from an agent are advisory until the configured stop policy accepts them; model agreement is not independent verification. Continuous conversation by itself does not certify a project complete.
